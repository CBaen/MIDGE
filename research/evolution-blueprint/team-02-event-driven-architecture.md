Risk Analysis: Out-of-Step-Order Signal Arrival\n\n**Current state — what actually breaks if signals arrive \"out of order\":**\n\nThe `ConvergenceAlerter` uses a time window (`domain_window` = 72h default). Signals expire based on `signal.timestamp`, not step count. So a 3-day-old congressional filing arriving \"late\" via API would already have `datetime.now() - timedelta(days=3)` as its timestamp and would fall outside the convergence window correctly. This is already handled.\n\nWhat is NOT handled: **two signals for the same ticker arriving in the same step** — the second one could overwrite the first in the per-ticker signal dict before `check_convergence()` sees both. This is not an out-of-order problem but a same-step collision problem. It's low probability and low impact.\n\n**Risks introduced by event-driven changes:**\n\n1. **Thread safety on ConvergenceAlerter**: The `record_signal()` and `check_convergence()` methods operate on `defaultdict` structures. If called from two threads simultaneously, you get dict mutation during iteration. **Fix**: add a `threading.Lock()` to `ConvergenceAlerter`. This is one line per method entry.\n\n2. **Alert deduplication**: If convergence check fires on signal arrival AND on step tick, the same alert could emit twice. **Fix**: the existing `_last_convergence_state` dedup in `_market_sense_hook` already handles this — it gates on direction change + material strength change.\n\n3. **Granger analysis on stale data**: Granger runs every 500 steps, consuming all accumulated signal history. If step pace changes, the cadence changes. Wall-clock conversion fixes this — Granger always runs on 30 min intervals regardless of pace.\n\n4. **Thompson feedback loop timing**: Outcome windows are in days (14-day pattern stack window). These are already wall-clock-anchored via `datetime.now()` in `OutcomeTracker`. No step dependency. Safe.\n\n5. **Archaeology excavation in background thread**: Already moved off main thread in the most recent session. Zero step dependency risk.\n\n**What definitively cannot break from event-driven changes:**\n- Mesa agent activation (agents still step normally — they have no market awareness)\n- ConnectionRegistry / HolonRegistry (infrastructure, step-independent)\n- Bootstrap (runs once, not per step)\n- Thompson distributions (only mutated by `record_outcome()`, which is explicitly called — not step-cadenced)\n\n---\n\n### 7.
